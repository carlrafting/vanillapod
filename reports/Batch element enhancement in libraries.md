# Batch enhancement leaves vanillapod's enhance() unusually strict

`enhance(elements, props, ...children)` is a sound primitive. Its main choices match what comparable libraries do, and its guards are stricter than any library surveyed. The collection wrappers (jQuery, Cash, Umbrella JS, Zepto) all apply one handler to every element in a set, and for direct listeners the element is exposed as `this` or `event.currentTarget`, which is the contract `enhance` documents. They also treat an empty set or a null target as a silent no-op, so `enhance([], ...)` returning `[]` is conventional. Three things set `enhance` apart. It is the only one that throws a TypeError when a DOM-node child meets a list: the four wrappers silently clone (jQuery, Cash, Zepto) or move (Umbrella, for detached nodes), and the hyperscript-style libraries read simply move the node, so the last target wins. It validates every entry before changing anything. And it accepts one mixed props object, where the libraries split the work across chained `attr()`, `prop()`, `css()` and `on()` calls. What `enhance` lacks, and what the declarative libraries (Stimulus, Alpine, htmx, Unpoly) all have, is an answer to repeated runs, teardown and later-inserted content. The real exposure is the `initX(root, selector)` layer, where calling an init function twice duplicates listeners. The most defensible next steps are to keep `enhance` as the lowest-level primitive, make `initX` idempotent with a `WeakSet`, and offer `AbortSignal`-based teardown. Most evidence is default-branch source on GitHub. The official documentation sites were unreachable, and the gaps are listed at the end.

## Everyone applies one handler to many elements, and the element identifies itself

The four collection wrappers converge on the same pattern. jQuery's dispatcher sets `event.currentTarget = matched.elem` and runs handlers with `.apply( matched.elem, args )`, so `this` equals `currentTarget` ([jQuery src/event.js](https://raw.githubusercontent.com/jquery/jquery/main/src/event.js)). Cash calls `callback.call(thisArg, event, ...)` with `thisArg` defaulting to the bound element ([Cash on.ts](https://raw.githubusercontent.com/fabiospampinato/cash/master/src/events/on.ts)). Zepto uses `callback.apply(element, ...)` ([Zepto event.js](https://raw.githubusercontent.com/madrobby/zepto/master/src/event.js)). Umbrella registers a wrapper through `node.addEventListener` for each node, so the native `this` and `currentTarget` apply ([Umbrella on.js](https://raw.githubusercontent.com/franciscop/umbrella/master/src/plugins/on/on.js)). Stimulus gets the same effect another way: it registers one native listener per target and fans out to bindings, and each binding calls the method on its own controller, so identity comes from the controller object and not from the event ([Stimulus binding.ts](https://raw.githubusercontent.com/hotwired/stimulus/main/src/core/binding.ts)). The inference is that `enhance(list, { onclick })` follows the dominant convention for direct listeners, and that `event.currentTarget` is the right documented identifier. It is native, and it avoids relying on `this`, which arrow functions cannot use. Vanillapod's own documentation already says this: every element gets the same listener, so use `event.currentTarget` ([enhancing-markup.md](/home/user/vanillapod/docs/enhancing-markup.md)).

One caveat applies, and it is an inference. In delegation, the wrappers set `currentTarget` to the matched descendant and not to the element carrying the listener ([jQuery event.js](https://raw.githubusercontent.com/jquery/jquery/main/src/event.js), [Cash on.ts](https://raw.githubusercontent.com/fabiospampinato/cash/master/src/events/on.ts), [Zepto event.js](https://raw.githubusercontent.com/madrobby/zepto/master/src/event.js)). Native events keep `currentTarget` as the listener's element ([MDN event bubbling](https://raw.githubusercontent.com/mdn/content/main/files/en-us/learn_web_development/core/scripting/event_bubbling/index.md)). `enhance` attaches native direct listeners, so its `currentTarget` is the native one. Anyone coming from jQuery's delegated style should know the semantics differ. This was not tested at runtime.

On removal, the wrappers support namespaces and `one`: jQuery, Cash and Zepto have dotted namespaces, and Umbrella's `on.js` and `off.js` show none, with its `off` needing the original callback reference ([Umbrella off.js](https://raw.githubusercontent.com/franciscop/umbrella/master/src/plugins/off/off.js)). `enhance` has no removal story. The platform offers one cheaply: the `signal` option on `addEventListener` removes the listener when the owning `AbortController` aborts, and BCD lists support from Chrome 90, Firefox 86 and Safari 15 ([MDN addEventListener](https://raw.githubusercontent.com/mdn/content/main/files/en-us/web/api/eventtarget/addeventlistener/index.md), [BCD EventTarget.json](https://raw.githubusercontent.com/mdn/browser-compat-data/main/api/EventTarget.json)). One signal can serve many elements, so batch teardown needs no registry. That all versions date to 2021 or earlier is an inference from the version numbers. No library read passes a signal, and none returns an undo function for imperative application; hyperscript's `h.cleanup()` is the nearest thing ([hyperscript index.js](https://raw.githubusercontent.com/hyperhype/hyperscript/master/index.js)).

## Node children are where libraries clone, move or ignore the problem

A DOM node can sit in only one place, and MDN says so directly: `appendChild` moves an attached node, `cloneNode` is the way to copy it, and clones do not carry listeners added with `addEventListener` or `onevent` properties ([MDN appendChild](https://raw.githubusercontent.com/mdn/content/main/files/en-us/web/api/node/appendchild/index.md), [MDN cloneNode](https://raw.githubusercontent.com/mdn/content/main/files/en-us/web/api/node/clonenode/index.md)). The libraries handle a multi-target insertion in different ways:

| Library | Multiple targets, one node | Source |
|---|---|---|
| jQuery | Original goes to the last target, deep clones (with events and data) to the others | [domManip.js](https://raw.githubusercontent.com/jquery/jquery/main/src/manipulation/domManip.js), [manipulation.js](https://raw.githubusercontent.com/jquery/jquery/main/src/manipulation.js) |
| Cash | Original goes to the first target, `cloneNode(true)` to the rest | [insert_selectors.ts](https://raw.githubusercontent.com/fabiospampinato/cash/master/src/manipulation/helpers/insert_selectors.ts) |
| Zepto | Clones for every target when the set has more than one element | [zepto.js](https://raw.githubusercontent.com/madrobby/zepto/master/src/zepto.js) |
| Umbrella | Clones in-page nodes, moves detached ones, so a detached node ends up only in the last target | [adjacent.js](https://raw.githubusercontent.com/franciscop/umbrella/master/src/plugins/adjacent/adjacent.js) |
| VanJS, hyperscript, Solid, Lit | Native move semantics, last placement wins | [van.js](https://raw.githubusercontent.com/vanjs-org/van/main/src/van.js), [hyperscript](https://raw.githubusercontent.com/hyperhype/hyperscript/master/index.js), [Solid client.js](https://raw.githubusercontent.com/ryansolid/dom-expressions/main/packages/dom-expressions/src/client.js), [lit-html.ts](https://raw.githubusercontent.com/lit/lit/main/packages/lit-html/src/lit-html.ts) |

The notes record that Mithril and Preact take vnodes, not DOM nodes, so the question does not arise there. Several of these results are read from paraphrased source summaries. The Zepto clone line was paraphrased, and Cash's `append.ts` was not read at all. Umbrella's detached-node outcome is a consequence of the code as read and was not run.

This supports `enhance`'s design. The two named choices for "which target gets the original" conflict (jQuery's last against Cash's first), so a user holding a reference sees the node in different places. Silent cloning loses `addEventListener` listeners unless the library copies them: jQuery's `clone(true)` copies events and data, Umbrella's `clone` copies its own registered listeners, and Cash and Zepto do not (the Cash and Zepto claims are inferred from the absence of an event-copy step). Throwing a TypeError for a node child with a list removes the ambiguity. None of the libraries surveyed throws in this case, so the guard is novel, with no direct precedent to lean on. Strings and numbers have no such problem, because each target can receive its own text node; `Element.append` already turns strings into Text nodes ([MDN Element.append](https://raw.githubusercontent.com/mdn/content/main/files/en-us/web/api/element/append/index.md)).

On props, the closest precedents for a mixed object come from the creation-oriented libraries. Preact's `setProperty` assigns a property when the name is `in dom`, with an attribute exception list, and removes on `null` or `false` except for `data-` and `aria-` names ([Preact props.js](https://raw.githubusercontent.com/preactjs/preact/main/src/diff/props.js)). VanJS looks for a prototype setter and falls back to `setAttribute`, treating keys starting with `on` as listeners ([van.js](https://raw.githubusercontent.com/vanjs-org/van/main/src/van.js)). Neither handles a `dataset` object; the idiom in these libraries is `data-*` attribute names. Of the libraries read, `van.add(dom, ...children)` is the closest to `enhance`'s children handling on an existing element, but it takes no props and no list. For `false` and null children, Solid skips booleans, while VanJS and Lit render `false` as text ([Solid client.js](https://raw.githubusercontent.com/ryansolid/dom-expressions/main/packages/dom-expressions/src/client.js), [lit-html.ts](https://raw.githubusercontent.com/lit/lit/main/packages/lit-html/src/lit-html.ts)). Vanillapod's children are limited to strings, numbers and (for a single element) DOM nodes, so this matters only if children widen later.

## Empty lists and invalid entries: libraries forgive, enhance validates

Every wrapper treats falsy input as an empty collection: jQuery's `init` returns an empty set for falsy selectors, Cash's constructor returns with length 0, Umbrella's `slice` returns `[]`, and Zepto returns an empty collection and strips `null` and `undefined` from arrays ([jQuery init.js](https://raw.githubusercontent.com/jquery/jquery/main/src/core/init.js), [Cash cash.ts](https://raw.githubusercontent.com/fabiospampinato/cash/master/src/core/cash.ts), [Umbrella slice.js](https://raw.githubusercontent.com/franciscop/umbrella/master/src/plugins/slice/slice.js), [Zepto zepto.js](https://raw.githubusercontent.com/madrobby/zepto/master/src/zepto.js)). jQuery's `domManip` on an empty set returns the collection untouched ([domManip.js](https://raw.githubusercontent.com/jquery/jquery/main/src/manipulation/domManip.js)). Zero matches is likewise a silent no-op in Stimulus, Alpine and htmx, as loops over empty sets. So `enhance([], props)` returning `[]` is consistent with everything read, and it keeps `enhance(document.querySelectorAll('.x'))` safe on pages where nothing matches.

Invalid entries are where `enhance` diverges. The libraries filter or skip per method: Cash's event methods skip entries that are not Element, Document or Window; jQuery's `event.add` returns early for nodes failing `acceptData`, and `jQuery.attr` returns `undefined` for text, comment and attribute nodes ([Cash on.ts](https://raw.githubusercontent.com/fabiospampinato/cash/master/src/events/on.ts), [jQuery event.js](https://raw.githubusercontent.com/jquery/jquery/main/src/event.js), [jQuery attr.js](https://raw.githubusercontent.com/jquery/jquery/main/src/attributes/attr.js)). The notes did not test what Umbrella or Cash do with a non-node array entry, and inferred that failures would surface in whichever method touches the entry, partway through. `enhance` validates every entry up front and throws before any change, which avoids half-applied batches. That is a deliberate strictness the libraries do not match, and it fits a helper whose callers hold lists from `querySelectorAll` and not hand-built arrays. The tradeoff is that a single bad entry blocks the whole batch, where the wrappers would skip it.

Two list-handling details are worth deciding explicitly. A live collection should be snapshotted before work: MDN notes `querySelectorAll` is the only API returning a static NodeList, while `childNodes` is live ([MDN NodeList](https://raw.githubusercontent.com/mdn/content/main/files/en-us/web/api/nodelist/index.md)). `Array.from` handles both; whether HTMLCollection is iterable was not confirmed from a source. And a duplicate entry in an array would be enhanced twice, which follows from "applies the same props to each" but was not tested.

## Repeated runs and teardown are the real gap, and they sit in initX

The declarative libraries answer a question `enhance` leaves open: what happens when the same element is processed twice. Stimulus tracks matched elements in a `Set`, so overlapping records cannot trigger duplicate callbacks ([element_observer.ts](https://raw.githubusercontent.com/hotwired/stimulus/main/src/mutation-observers/element_observer.ts)). Alpine skips any element carrying an `_x_marker` expando and deletes the marker on teardown ([lifecycle.js](https://raw.githubusercontent.com/alpinejs/alpine/main/packages/alpinejs/src/lifecycle.js)). htmx compares a hash of the element's attributes and re-initialises only when it changed ([htmx.js](https://raw.githubusercontent.com/bigskysoftware/htmx/master/src/htmx.js)). Teardown is symmetric with setup in all of them: htmx records each listener and removes it in `deInitNode`, and Stimulus clears its cached listener only for disconnected elements because caching them "would retain the element" ([binding_observer.ts](https://raw.githubusercontent.com/hotwired/stimulus/main/src/core/binding_observer.ts)). Unpoly lets a compiler return a destructor, per a search summary of its docs only ([up.destructor](https://unpoly.com/up.destructor)).

Vanillapod's `initCopyButtons` loops `root.querySelectorAll(selector)` and adds a fresh anonymous `click` listener per button, with no marker, dedupe or cleanup ([copy-button.js](/home/user/vanillapod/components/copy-button/copy-button.js)). Calling it twice on the same root therefore doubles the listeners. This is an `initX` problem and not an `enhance` one: `enhance` is explicit about applying props to what it is given, and the libraries' guards live in the discovery layer, not in the apply layer. The notes also show that `initX(root, selector)` resembles htmx's `process(root)` and Unpoly's compilers: a root-scoped, re-runnable scan, with the selector as a parameter. It differs in registering nothing globally.

Later-inserted content splits the field. Stimulus and Alpine use a document-level `MutationObserver`; Alpine pauses it during its own writes and treats a node in both the added and removed lists as a move ([Alpine mutation.js](https://raw.githubusercontent.com/alpinejs/alpine/main/packages/alpinejs/src/mutation.js)). htmx re-processes only what it swaps in, plus explicit `htmx.process` calls. `initX(newFragment)` is in the manual, htmx-like camp. Delegation, one ancestor listener with `event.target.closest(selector)`, covers future elements without re-running anything, but only for events that bubble. MDN confirms `focus` does not bubble and `focusin` does ([MDN focusin](https://raw.githubusercontent.com/mdn/content/main/files/en-us/web/api/element/focusin_event/index.md)). Which other events fail to bubble is general knowledge in the notes and unsourced.

## What vanillapod could do next

These are options, not findings of any source. The first, which the evidence favors most, is to leave `enhance` as the pure apply primitive and document its guards as deliberate: the TypeError for node children with lists, up-front validation, and `currentTarget` as the identifier. The platform gives users `Array.from` and `append` already, so `enhance` earns its place on the combination of props, listeners and children in one call, and on the list form's fan-out, which mirrors the `ref` and `use:` pattern in Solid and Lit. The Lit notes add a caution that a single `Ref` object across many elements keeps only the last, so per-element callbacks are the safer model ([Lit ref.ts](https://raw.githubusercontent.com/lit/lit/main/packages/lit-html/src/directives/ref.ts)).

The second is to fix the `initX` duplicate-listener problem, with three levels of effort. The cheapest is a module-level `WeakSet` of already-initialised elements, which matches the Set (Stimulus) and marker (Alpine) idioms without adding an expando or leaking. A second is to scope listeners with an `AbortSignal`, either passed in or created inside and returned as a cleanup function in the Unpoly style, which allows re-adding after teardown and needs no listener registry like htmx's. A third, if the project wants auto-enhancement of any insertion, is a `MutationObserver` that calls `initX` on added subtrees, but this brings the move, wrap and idempotence subtleties Alpine had to solve, and the notes found no need for it today. The `WeakSet` and the signal are compatible: an aborted signal could also clear the set entry.

The third is optional additions to `enhance` itself. It could accept a `signal` prop or option so a batch of listeners can be torn down with one `abort()`; since the platform already supports this, it fits naturally. Its array return already differs from the wrappers, none of which returns a plain array, so chaining is not a precedent to follow. A children policy for `null`, `undefined` and `false` could be written down, with skipping `false` matching Solid's choice. The `dataset` and dashed attribute handling is already ahead of the libraries read, none of which handled a dataset object. Against these, cloning node children per target (the jQuery, Cash and Zepto route) is the option the evidence argues against: it hides which target holds the original, and clones lose `addEventListener` listeners unless the helper re-applies them, which `enhance` could do on the clone. If node children for lists are wanted, an explicit factory form such as a function child called per element avoids the ambiguity while keeping the guard. That is a design suggestion with no precedent in the sources.

Finally, native alternatives may reduce the need over time but do not replace it today. Custom elements attach behavior through `connectedCallback`, but customized built-ins (`is=`) are not supported in Safari, and MDN says Safari does not plan to support them ([MDN using custom elements](https://raw.githubusercontent.com/mdn/content/main/files/en-us/web/api/web_components/using_custom_elements/index.md), [BCD CustomElementRegistry.json](https://raw.githubusercontent.com/mdn/browser-compat-data/main/api/CustomElementRegistry.json)). A custom-attributes proposal is under discussion in WICG/webcomponents issue 1029, with a minimal MVP being drafted as of early 2026 and nothing shipped in the sources found ([WICG issue 1029](https://github.com/WICG/webcomponents/issues/1029)).

## Limits of this research

Most official documentation was unreachable from the researchers' network: MDN, WHATWG, caniuse and web.dev, and the sites of Stimulus, Alpine, htmx, Unpoly, jQuery, Umbrella JS, Zepto, VanJS, Lit, Solid, Preact and Mithril. Claims therefore rest on default-branch source on GitHub, read through a summarizing fetch tool, so quotes are near-verbatim and some function behavior is paraphrased. MDN claims come from the MDN source repository (mdn/content and mdn/browser-compat-data), and WHATWG spec text was not read. Versions are `package.json` values on default branches, not confirmed releases: jQuery `main` reads 4.1.0, which was not confirmed as a published release; Cash 8.1.5, Umbrella 3.3.4, Zepto 1.2.0, Stimulus 3.2.2, Alpine 3.17.5, htmx 2.0.11 on `master` (another branch may be newer), VanJS 1.6.2, Preact 11.2.0, Solid 2.0.4, lit-html 3.3.3 and Mithril 2.3.8. Behavior is "as of the source read on 2026-11-28", and release notes were not read, so nothing is claimed about changes between versions.

Specific gaps follow. Unpoly is thinly covered: only a search-result summary of its docs on destructors and `up.destroy`, with its version, selector semantics, compile timing and once-per-element guarantee unverified. The `:has()` and `:is()` support was not verified (the `:has` source URL returned 404), and no Baseline or caniuse labels were read. That `mouseenter`, `mouseleave`, `blur`, `load` and `scroll` do not bubble is general knowledge, unsourced here; only the `focus` and `focusin` pair was confirmed. HTMLCollection live behavior and iterability, the `<template>` page, shadow-DOM retargeting, custom-element hyphen naming rules and DOM Parts browser status were not sourced. Umbrella `once` is unconfirmed (no file found at the expected path), Zepto's `one` combined with delegation over several elements is a reported caveat not independently verified, and Cash's `append.ts` and Zepto's insertion code were not read in full. Several statements are inferences and are labelled as such above: that jQuery's `one` fires once per element, that Cash and Zepto clones lose listeners, how non-node array entries behave in Umbrella and Cash, and that the signal option is safe without a polyfill. No runtime test of any library or of `enhance` against these patterns was run, and the repo test `/home/user/vanillapod/tests/browser/elements.test.ts` was not read in detail. Whether `abort()` is a no-op for an already-aborted signal passed at add time was not verified. No performance comparison of N listeners against delegation was found.

## Conclusion

The sharpest finding is an asymmetry. Across the libraries surveyed, `enhance`'s guards (the TypeError, up-front validation) have no precedent, while its core semantics (shared handler, element via `currentTarget`, empty list as a no-op) match common practice. That makes the guards a design position vanillapod owns and should document as intentional, not a convention it inherits.

The more consequential implication is that the surveyed libraries solve a different problem from the one vanillapod's tests exercise. Their hard parts are idempotence, teardown and late content, and all three live above `enhance`, in `initX`. A `WeakSet` guard plus signal-based cleanup would close the known duplicate-listener hazard at small cost, while observers and delegation stay optional until a concrete use case needs them.
